# Thought Machine FDE Agent Skills: Workshop Agenda & Hands-On Runbook

In this workshop attendees build, test and package the **Notice Saver** deposit product on Thought Machine Vault Core using AI agent skills. The smart contract, its tests and its CLU pack are generated by the attendees: they are the exercise and are not distributed.

---

## Distribution model

Attendees receive **one bundle**, before the workshop. It contains the skills, the Inception SDK, the Contracts SDK and the starter project (the product brief, an empty product skeleton and no contract):

```text
workshop/
├── contracts_sdk/contracts_sdk/     Contracts SDK (already extracted)
├── inception_sdk/                   Inception SDK
├── fde-agent-skills/                the skills (install.sh is here)
├── starter-project/                 <-- you work here
└── WORKSHOP_AGENDA.md
```

1. **Before the workshop**: attendees unzip the bundle and complete `starter-project/PREREQUISITES_CHECKLIST.md` (virtual environment, packages, importable SDKs, CLU binary, Vault connection). `bash preflight.sh` confirms they are ready.
2. **Workshop day**: attendees register the skills (`./install.sh` in `fde-agent-skills/`) and start building.

## Teams that already have some of this: check, then skip

The client engineering team has already worked on smart contracts, so for each stage below do a **quick check**. If the team already has the output, validate it and move on instead of regenerating it.

### Setup

| Already have | Quick check | Then |
| :--- | :--- | :--- |
| Python environment, Contracts SDK, Inception SDK, Feature Library | `bash preflight.sh` is all ✅ | Skip setup. Use your own library versions if they match your Vault version. |
| CLU 5.x | `clu --help` | Skip the CLU step. |
| Vault sandbox and token | preflight shows HTTP 200 | Skip. Reuse your own environment config through `INC_ENVIRONMENT_CONFIG_PATH`. |

### Delivery stages

| Stage | If the team already has... | Quick check | Then |
| :--- | :--- | :--- | :--- |
| 1. Requirements | A requirements or PRD document | Place it at `documentation/REQUIREMENTS.md` | Run `/clarify-requirements` in review mode to close gaps only, or skip if it is already complete and structured |
| 2. Test plan | A test plan, or existing tests | Place the plan at `documentation/TEST_PLAN.md` | `/create-test-plan` can derive a plan from existing tests and requirements. Skip if it traces every requirement. |
| 3. Smart contract | A CLv4 contract | Does it render and pass its existing tests? | Do not run `/create-smart-contract` over it. Use `/update-smart-contract` for a change, `/modernise-feature` to bring an older feature up to current library conventions, or `/convert-clv3` for a CLv3 contract. |
| 3. Smart contract | Individual features already built | Is the feature in `feature_library`, or in your own repo? | Compose it in the recipe contract and build only the features you lack |
| 4. CLU pack | Parameters, flags, accounts, a manifest | `clu validate <manifest>` passes | Run `/create-clu-resources` only for features that are not packaged yet |
| 5. Tests | Unit and simulation tests | The suite passes against your Vault | Run `/create-sc-tests` only for scenarios not covered |
| 6. Review | Your own review process | n/a | `/code-reviewer`, `/adversarial-review` and `/explainer-skill` are optional extras, run them when you want a second look or business documentation |

## How the product is built: one feature at a time

```
 /clarify-requirements  ->  REQUIREMENTS.md
 /create-test-plan      ->  TEST_PLAN.md
 /create-smart-contract ->  IMPLEMENTATION_PLAN.md   (first run: the plan for the whole product)

 For each feature (small, self-contained, validated before the next):
     /create-smart-contract   build the feature
     /create-clu-resources    add its parameters, flags, accounts, schedules; clu validate
     /create-sc-tests         unit and simulation tests; run them

 After the last feature:
     /create-sc-tests         end-to-end tests
     /code-reviewer  ->  /adversarial-review  ->  /explainer-skill
```

* The contract is a **recipe** (`contracts/template/`): it wires **features** together. A feature is a reusable business capability: either a `feature_library` module used as it is, or a product-specific module under `features/`. Helpers that are not business features go in `common/`.
* **Unit tests** need no Vault. **Simulation tests** call the Vault simulator, so they need the connection from the checklist. **End-to-end tests** create real accounts in the Vault environment.

## Day-of setup (10 minutes)

1. **Install the skills.** They are already in the bundle, in `fde-agent-skills/` next to `starter-project/`:
   ```bash
   cd fde-agent-skills            # the folder that contains install.sh
   chmod +x install.sh && ./install.sh
   ```
   (Gemini CLI alternative: `gemini extensions install $(pwd)`.)
2. **Enter the project** and activate the environment:
   ```bash
   cd ../starter-project
   source .venv/bin/activate
   export INC_ENVIRONMENT_CONFIG_PATH=environment.json INC_ENVIRONMENT_NAME=sandbox
   bash preflight.sh
   ```
3. **Start your AI tool** (`claude`, `gemini`, ...) from `starter-project/` and check that `/clarify-requirements`, `/create-test-plan` and `/create-smart-contract` are listed.

## Agenda (about 3 hours)

The reference build has seven features. In the session, build **Features 1 and 2** end to end, and **Feature 5** (notice lodgement) as a stretch. Features 1 and 2 are the basic validation features and Feature 5 is the first custom one that other features depend on.

### Module 1: Welcome and setup check (15 min)
* Run the day-of setup and `bash preflight.sh`.
* Briefing: skills are local markdown and AsciiDoc files, so they need no internet and no registry access. `common-references` holds the Vault 5.9 Contracts API, Core API and CLU documentation and the Inception test framework guides, which the skills use as ground truth instead of guessing.

### Module 2: Requirements (25 min)
* `/clarify-requirements` with the product brief in `src/notice_saver/documentation/`.
* Experience the multi-turn interview, then review `REQUIREMENTS.md`: parameters, accounting entries, schedules and acceptance criteria. Open items marked `TBC` are closed later, at the CLU stage.

### Module 3: Test plan (20 min)
* `/create-test-plan`, then review `TEST_PLAN.md`: scenarios, worked numbers, and the traceability table from every requirement to a scenario.

### Module 4: Plan and first features (60 min)
* `/create-smart-contract`: read `IMPLEMENTATION_PLAN.md` first (how each feature maps to library modules, decisions, open questions). Answer its questions (for example the Vault version).
* Build **Feature 1**, then run `/create-clu-resources` and `/create-sc-tests` for it before starting Feature 2. Notice how the unit tests need no Vault and how the simulation tests assert rejection reasons.
* Repeat for **Feature 2**. If time remains, plan and build **Feature 5**.

### Module 5: Package and validate (20 min)
* In `/create-clu-resources`, answer the questions about `TBC` values (internal account IDs).
* Run `clu validate src/notice_saver/manifest.yaml`. Optionally import the pack into your sandbox (see the notes below).

### Module 6: Test run and wrap-up (30 min)
* Run the whole suite: `python -m pytest src/notice_saver/tests -n 4`. (This only works once `/create-sc-tests` has written tests. Before that, "no tests ran" with exit code 5 is normal.)
* Inspect any failure. The skills diagnose whether the contract, the test plan or the test is wrong, and do not change an expected value to make a test pass.
* Q&A, the remaining features, and the optional review skills (`/code-reviewer`, `/adversarial-review`, `/explainer-skill`).

## Notes on importing the pack into a Vault environment

Only do this on a sandbox you are allowed to write to.

* Render the contract into `contracts/notice_saver_rendered.py` before `clu import` (the file is an empty placeholder until then, and `clu validate` does not need it filled), and reset it to empty afterwards.
* CLU creates resources and cannot update them. A parameter or internal account that already exists in the environment returns **409**, and CLU then reports **partial success**. This is expected, and the existing resource is reused. Only genuine errors (for example a 400) need fixing.
* In Vault 5.9 and later, product-level values for a CLv4 contract are `PARAMETER_VALUE` resources under a parameter value hierarchy node (the skill generates them). Create accounts for the product on that node.
* `clu validate` is an offline check and does not catch everything Vault checks on import.

## Day-of troubleshooting

| Issue | Cause | Solution |
| :--- | :--- | :--- |
| The AI tool does not show `/clarify-requirements` | Skills not registered | Run `./install.sh` in `fde-agent-skills`, then restart the tool. |
| `ModuleNotFoundError` for `notice_saver` or `inception_sdk` | Virtual environment not active, or `workspace.pth` incomplete | `source .venv/bin/activate`, then repeat the `.pth` step in the checklist. |
| `No environment_name found` | The `INC_` variables are not exported in this terminal | `export INC_ENVIRONMENT_CONFIG_PATH=environment.json INC_ENVIRONMENT_NAME=sandbox` |
| Simulation tests cannot connect | Wrong URL or token, or no VPN | `bash preflight.sh`; a 401 is a bad token, a timeout is usually the VPN. |
| `clu: permission denied` | Binary not executable | `chmod +x` the binary. |
| Render fails with a missing module | A template file named like its package | The renderer registers the template under its file name; name the template differently from the product package (for example `notice_saver_template.py`). |
| Simulation shows the activation hook failing on `ScheduledEvent` timezone | The contract sets `events_timezone` but a schedule starts in UTC | Convert the schedule's `start_datetime` to `vault.events_timezone`. |
| A notification fails with "not defined in contract metadata" | The notification type is not listed in `notification_types` | Declare every notification type the contract emits. |
| Rendered contract fails in Vault with an undefined name | An empty list declared as `x: list = []` in a feature module is not rendered | Do not declare empty `expected_parameters` or `data_fetchers` lists; omit them. |
| Vault rejects a hook for duplicate fetcher IDs | The same fetcher listed twice in one `@fetch_account_data` | Remove the repeated ID (features often share a fetcher). |
| `clu import` returns 400 on an internal account | `permitted_denominations` set on an internal account | Remove it from internal account resources. |
